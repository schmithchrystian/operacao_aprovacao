## Validação, revisão e reversão

Para cada alteração de produto: regressão comportamental antes/depois; lint, typecheck, testes e build serializado com o dono do checkout. Mudanças de schema exigem validação Prisma, migration aplicada em banco isolado e compatibilidade testada. Integration tests devem conferir persistência e constraints; mocks não bastam para as ordens 2–6.

Reversão proposta: mudanças pequenas e compatíveis por etapa; migrations aditivas primeiro e remoções somente após dados/código migrarem. Feature flag pode desabilitar fluxo incompleto. Rollback de código só depois de verificar compatibilidade com schema e eventos persistidos; nunca reabrir mock em produção como fallback. Restauração de dados requer procedimento previamente testado por Dados/SRE, não promessa de desfazer writes com git revert.

Validações nesta rodada: inspeção de fontes e contagem de stubs; QA executou as seis reproduções e compartilhou resultado. Logs existentes consultados: 744/107 aprovados, lint/typecheck sem diagnósticos e build mock concluído segundo relatório da auditoria. Dev não reexecutou build nem testes completos e não instalou dependências.

Resultado: **alterações necessárias**. Arquivos criados pelo papel Dev: somente este relatório. Entidades, migrations, endpoints e componentes alterados: nenhum. Próximo responsável: PMO atribui um dono de escrita por entrega; Dev implementa com Dados/Cloud conforme dependência; QA/SEC/Revisão validam de forma independente. Melhoria preventiva: critério de pronto por fluxo completo em staging com Postgres, com evidência antes/depois anexada à mudança e backlog de incidentes/retrabalho mensurado quando houver histórico.
